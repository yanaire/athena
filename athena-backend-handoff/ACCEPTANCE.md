# 실제 백엔드 인수 기준

작성일: 2026-11-20

이 문서는 **앞으로 구현할 실제 서비스의 인수 검사**다. 아래 항목을 이미 통과했다는 보고서가 아니다. 기존 93개 DOM 통합 검사와 51개 계약 검사는 fixture 기반이며, 실제 모델·프로세스·저장소·브라우저 검사를 대신하지 않는다.

상세 계약은 [인계서](athena-backend-handoff.md), 구현 전에 보완할 항목은 [CONTRACT-GAPS.md](CONTRACT-GAPS.md)를 따른다. 기능이 현재 계약에 없으면 UI·타입·호스트 변경을 먼저 합의하고 검사한다.

## 기록 방법

각 항목에 다음 내용을 기록한다.

- 결과: PASS / FAIL / BLOCKED / NOT RUN. 미실행을 PASS로 표시하지 않는다.
- 코드 commit, SDK 버전·lockfile, OS·브라우저, 실행 명령
- 실제 project/session/run/task/tool/artifact/source/document ID와 버전
- 재현 절차, 실제 관측 결과, 기대 결과
- 로그·스크린샷·저장 전후 해시·재조회 응답 중 해당 동작을 증명하는 자료

로그에는 자격 증명을 넣지 않는다. 실패 주입 시 어느 경계를 끊었는지 기록한다. 비용이 드는 provider 검사는 개발 환경에서 작은 요청으로 수행하되, fixture 응답으로 바꾸면 별도 fixture 검사로 표시한다.

## A. 연결과 모델

| ID | 시나리오 | 통과 조건과 증거 |
| --- | --- | --- |
| A01 | Validate format 실행 | 형식 검사만 수행한다. 네트워크·저장·세션 생성 호출이 발생하지 않는다. |
| A02 | 실제 연결 확인: 정상 endpoint와 잘못된 인증 | 실제 I/O 결과를 표시한다. 실패가 connected로 바뀌지 않는다. 이 동작만으로 설정을 저장하거나 새 대화를 만들지 않는다. |
| A03 | Models의 Save settings, 저장 실패 주입 | 실제 저장 뒤 configurationId와 saved receipt가 반환된다. 실패 시 기존 확정 설정을 보존한다. 다시 읽은 설정이 저장 값과 일치한다. |
| A04 | 앱 기본·프로젝트 기본·현재 대화·실행 시작 모델 변경 | 새 대화의 해석 순서가 계약과 일치한다. 이미 시작된 run의 모델은 이후 설정 변경으로 바뀌지 않는다. |
| A05 | 실제 모델 목록·검색·reasoning 지원 | 실제 제공 가능한 모델과 지원 수준을 표시한다. 지원하지 않는 선택은 명시적으로 실패하고 이전 확정 선택을 보존한다. |
| A06 | 재시작 후 연결 설정 로드 | getState는 동기 cache를 제공하고 비동기 초기 결과는 subscribe로 반영한다. 저장 기록이 있다는 이유만으로 연결 확인 완료라고 표시하지 않는다. |

## B. 생성·전환·전송과 첨부

| ID | 시나리오 | 통과 조건과 증거 |
| --- | --- | --- |
| B01 | 대화 B 생성 완료, Pi 프록시는 아직 A | B의 입력이 A로 전송되지 않는다. 실제 B의 ID와 바인딩이 준비된 뒤 전송한다. |
| B02 | Pi 프록시가 B로 먼저 전환, TaskManager snapshot은 아직 A | A의 project/run/task를 B 요청에 붙이지 않는다. 불일치를 사용자에게 표시한다. |
| B03 | 세션 생성 성공 후 제목·모델 적용 실패 | 생성 성공과 후속 실패를 구분한다. 재시도 때문에 같은 의도의 세션을 중복 생성하지 않는다. |
| B04 | New research, Add project, 현재 초안 작성 | 세 동작이 분리되어 있다. 실제 세션 생성 receipt 이전에는 새 대화가 생성된 것처럼 전환하지 않는다. |
| B05 | 공백·개행·비 BMP 문자를 포함한 긴 입력 | 전송한 원문이 정확하다. 기본 한도 262144 UTF-16 단위를 넘는 입력은 절단 없이 거절한다. 전체 초안·첨부를 보존한다. 한도를 바꾸었다면 광고한 실제 값으로 검사한다. |
| B06 | prepare/staging 도중 사용자가 입력과 첨부 수정 | 완료된 이전 준비 작업이 새 초안을 지우거나 새 파일을 잘못 전송하지 않는다. |
| B07 | 전송 ack 이전 단절과 뒤늦은 응답 | 원문·첨부를 보존하고 실제 접수 여부를 조회한다. 불확실한 상태에서 자동 중복 실행하거나 성공으로 표시하지 않는다. 재연결 중복 방지 정책을 증명한다. |
| B08 | 부분 staging, 잘못된 프로젝트·버전의 file ref, 파일 읽기 실패 | 모든 참조가 검증되지 않으면 provider 호출 전에 실패한다. 이름·크기 metadata만으로 읽기 완료 처리하지 않는다. |
| B09 | UI와 호스트를 별도 프로세스로 분리 | File bytes가 실제로 전달되고 세션별 프록시가 동작한다. JSON에 함수를 넣어 전달했다고 가정하지 않는다. 다른 세션으로 요청·응답이 섞이지 않는다. |

## C. 실행과 이벤트

| ID | 시나리오 | 통과 조건과 증거 |
| --- | --- | --- |
| C01 | 같은 메시지에 done → message_end, 역순, 재전달 | 지원하는 조합에서 완료 메시지가 한 번만 추가된다. 내용이 같은 서로 다른 두 메시지는 합치지 않는다. |
| C02 | 응답이 필요한 extension 요청 25개 이상 | 화면 페이지 제한과 무관하게 모든 pending이 보존된다. 취소는 원래 요청·연결에 전달된다. 전달 실패 시 미응답 요청이 사라지지 않는다. |
| C03 | 실제 Pi만 연결 / 빈 TaskManager snapshot / 호스트 단절 | 샘플 프로젝트·샘플 완료 작업을 실제 실행으로 표시하지 않는다. 미연결·빈 상태·오류를 구분한다. |
| C04 | 한 번 전송해 실제 도구를 수행 | provider 실행 접수와 root run/task 생성이 한 번 이루어진다. 채팅·Workflow·Agents·Execution·Artifacts가 같은 scope ID를 참조한다. |
| C05 | snapshot 역순·중복, 전환 이전 연결의 늦은 이벤트 | 이전 revision과 이전 연결 응답을 무시한다. 같은 구독의 revision은 세션 전환 후에도 증가한다. 전체 snapshot의 범위가 명확하다. |
| C06 | 정상 종료·자동 재시도·큐 후속 작업·취소 | 단순 agent_end만으로 전체 실행 성공을 확정하지 않는다. 실제 idle/settled와 작업자 종료를 확인한다. 취소 접수와 실제 종료를 구분한다. |
| C07 | 작업 재시도 | 시도를 구분하며 이전 로그·결과물을 보존한다. 실패한 이전 시도가 새 시도의 완료 이벤트로 덮이지 않는다. UI에 새 상태·attemptId를 노출하면 타입과 처리기를 함께 검사한다. |
| C08 | 승인이 필요한 실제 작업 | 승인 전에는 실제 작업을 수행하지 않는다. 거절·취소·만료가 승인으로 바뀌지 않는다. TaskManager approval과 Pi extension dialog를 서로 바꿔 응답하지 않는다. |
| C09 | 두 작업자가 동일한 raw toolCallId 생성 | canonical ID는 충돌하지 않는다. 부모 대화의 scope와 실제 worker Pi ID 매핑을 추적할 수 있고 메인 최종 메시지가 작업자 답변으로 오염되지 않는다. |

| D03 | PDF 미리보기 성공, 추출 미실행·실패·성공 | preview와 extraction 상태가 독립적이다. ready는 정확한 source version의 실제 text를 포함한다. |

| D08 | source v2 저장 후 v1 추출 완료가 늦게 도착 | v1 결과는 v1에 보존하고 현재 head를 되돌리지 않는다. 목록 병합·삭제·페이지 처리 정책도 계약과 일치한다. |
| D09 | pending 요청·실행 중 호스트 crash | 복구·종료·미확인 처리 정책이 실제 상태와 일치한다. 자동 승인·성공·완료를 만들지 않는다. 남은 프로세스와 세션을 재조정한다. |
| D10 | bounded preview를 넘는 도구 출력 | 미리보기 제한이 표시된다. 지원하는 범위에서는 원문 저장·조회로 전체 출력을 읽을 수 있다. 미지원이면 완료된 원문 보관으로 표시하지 않는다. |

## E. 실제 브라우저와 접근성

다음 항목은 DOM mock이나 정적 CSS 검색으로 통과시킬 수 없다. 실제 화면과 입력 장치로 검사한다.

| ID | 시나리오 | 통과 조건과 증거 |
| --- | --- | --- |
| E01 | 기존 화면의 모든 주요 경로 | 영어 UI, 기존 모델 picker, 한 개의 오른쪽 toggle, 인라인 도형 에이전트, 조용한 도구 표시, 패널 조절이 유지된다. |
| E02 | 좁은 폭·낮은 높이·확대·가상 키보드 | 폭 390px/744px와 높이 400px 전후를 포함해 입력창·모달 하단 버튼에 접근할 수 있다. 화면 확대·가상 키보드에서 잘림과 의도치 않은 가로 스크롤을 확인한다. |
| E03 | sidebar/panel의 drawer 전환과 모델 listbox | 크기 변경 중 포커스가 inert 영역에 남지 않는다. Tab은 다음 조작부로, 방향키는 선택지 사이로 이동한다. Escape·포커스 복귀·스크린 리더 이름을 검사한다. |
| E04 | 실제 토큰 지연·도구 실행·답변 생성·실패·완료 | 모션은 실제 상태를 따라가며 실패·완료 뒤 멈춘다. 모델의 비공개 추론 원문을 진행 상태 표시로 요구하지 않는다. reduced-motion 설정에서도 상태를 이해할 수 있다. |

## 단계별 사용

M1에서는 A01–A05, B01–B09의 해당 경로, C01/C03/C04, D01을 우선한다. 전체 기능 납품에서는 나머지 항목을 완료하거나 미구현 사유와 영향을 명시한다. 선택하지 않은 기능을 허위로 PASS 처리하지 않는다.

첫 납품의 최소 증거는 **실제 파일 읽기와 모델 답변 한 건의 ID 연결 로그, 재시작 뒤 재조회, 실패 한 건에서 초안 보존, 실제 화면 확인**이다.
