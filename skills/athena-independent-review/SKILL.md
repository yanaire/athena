# 독립 근거 검토

주장과 확인 가능한 근거를 대조하여 판정과 수정 요구를 제시하라.
review verdict는 Knowledge 승격·문서 승인·배포 권한을 부여하지 않는다.

## 입력

- 검토할 주장과 artifact/file 참조, 버전 또는 내용 hash를 확보하라.
- 원시 자료·계산 로그·방법·단위·공개된 평가 기준을 수집하라.
- 작성자와 검토자의 실제 session/model 정보, 도구 capability와 허용 입력을 확인하라.
- 자료가 누락되면 이름으로 내용을 추정하지 말고 누락 항목을 표시하라.

## 독립성 확보

1. 독립 실행이 가능하면 작성 세션과 다른 실제 Pi 세션에서 검토하라.
2. 현재 M2 child는 새 child를 만들 수 없으므로 필요한 위임은 parent가 수행하게 하라.
3. 검토 세션이 없으면 같은 세션 재점검으로 명시하고 독립 검토 완료라고 부르지 마라.
4. 같은 모델의 별도 세션도 공통 편향을 가질 수 있음을 기록하라.
5. 원본 근거와 공개 기준을 전달하고 작성자의 숨은 추론·유도된 정답을 전달하지 마라.
6. 검토 대상의 명시적 주장과 비공개 평가 정답·숨은 실패 위치를 구별하라.
7. 숨은 정답·평가 라벨을 reviewer prompt, 첨부 grant, 공유 파일에 노출하지 마라.
8. backend의 실제 grant 상속 때문에 격리를 보장할 수 없으면 그 한계를 기록하라.
9. 입력 격리가 필요한 평가라면 검토 패키지만 준비하고 검증된 별도 경로를 기다려라.

## 검토 절차

- 원시 근거를 직접 읽고 주장별로 지지·반박·미확인 항목을 대응시켜라.
- 관측된 도구로 가능한 핵심 계산을 재확인하고, 실행하지 못한 검사는 미실행으로 남겨라.
- 표본 수·단위·결측·변환·불확실성·인과 표현·실패한 계산의 처리 여부를 확인하라.
- 자료의 모순과 판단의 불확실성을 별도로 적고, 근거 위치와 재현 조건을 제시하라.
- 자료가 불충분하면 승인 대신 insufficient_evidence를 선택하라.
- 검토 후 원문이나 결과 버전이 바뀌면 기존 verdict를 새 버전에 자동 적용하지 마라.

## 현재 통합 경계

현재 M2에 전용 reviewer workflow나 문서 버전 승인이 연결됐다고 가정하지 마라.
child read는 허용된 입력만 읽으므로 artifact URI가 있다는 이유로 읽을 수 있다고 판단하지 마라.
필요한 조회·재계산·검토 저장 capability가 없으면 검토 요청 패키지 또는 응답 내 판정을 반환하라.
실제 저장 receipt가 없으면 review ID와 persisted 상태를 만들어 내지 마라.
TaskManager의 task/attempt 종료 상태는 변경하지 말고 관측값으로만 기록하라.

## 구조화된 출력

| 필드 | 기록할 내용 |
|---|---|
| target | 실제 대상 ID·버전/hash·주장 |
| reviewer | 실제 session/model·작성자와의 관계·격리 한계 |
| checks | 수행 검사·근거 위치·결과·미실행 이유 |
| findings | 영향·근거·재현 조건·필요 수정 |
| verdict | supported / changes_required / insufficient_evidence |
| coverage | 검토 범위·제외 범위·남은 불확실성 |
| persistence | 실제 review receipt 또는 not_persisted |

## 자체 예시와 인수 조건

원시 CSV와 그 통계를 설명하는 초안을 별도 검토 세션에 제공하라.
공개 기준은 행 수·단위·계산 방법으로 정하고 비공개 정답표는 제공하지 마라.
판정이 초안 문구의 반복이 아니라 읽은 근거와 수행한 검사에 연결되는지 확인하라.
같은 모델 사용, 계산 도구 부재, 입력 격리 실패를 숨기지 않으면 검토의 한계가 전달된 것이다.
