# 연구 요청 정리

사용자의 질문을 검증 가능한 목표와 최소 실행 범위로 바꾸어라.
이 문서는 Athena 저장소용 절차이며, 도구 설치·권한·자동 스킬 선택 기능을 추가하지 않는다.

## 입력

- 사용자 원문, 기대 산출물, 이미 합의된 제약과 허용 범위를 읽어라.
- 관측된 project/session/run ID, 첨부 file ID와 버전, 출처를 수집하라.
- 현재 세션의 실제 도구 목록·입력 스키마·capability 응답을 확인하라.
- 기한·비용·데이터 범위가 주어졌다면 보존하고, 없으면 미지정으로 남겨라.

## 절차

1. 사용자가 답을 원하는 질문을 한 문장으로 적어라.
2. 설명·비교·예측·인과 검증 중 필요한 판단을 구별하라.
3. 대상, 측정 변수, 단위, 관측 단위, 비교 조건을 정리하라.
4. 알려진 사실, 사용자가 제시한 주장, 작업 가정을 구별하라.
5. 자료마다 실제 접근 여부와 읽은 범위를 확인하라.
6. 파일명·미리보기만 보고 본문을 읽었다고 판단하지 마라.
7. 완료 기준을 산출물과 검사 방법으로 적어라.
8. 결론을 바꿀 필수 정보만 질문하고, 안전한 가정으로 진행할 부분은 명시하라.
9. 이미 허용된 범위의 읽기·정리는 계속하고, 승인을 반복해서 요구하지 마라.
10. 실행 가능한 다음 단계와 capability가 없어 제안에 머무는 단계를 표시하라.

## 실행 경계

- TaskManager만 task·attempt·scheduler 상태를 소유하게 하라.
- 실제 응답에서 확인한 ID만 실행 기록에 넣고, 없는 ID는 null로 남겨라.
- 현재 M2 child의 기본 도구는 허용 파일 read와 고정 calculate_csv임을 반영하라.
- 검색·일반 Python·공학 솔버·문서 버전 저장이 목록에 없으면 사용 가능하다고 쓰지 마라.
- skill 파일의 존재를 실제 로딩·실행 또는 backend 통합 완료로 해석하지 마라.
- 연구 브리프의 준비 상태와 backend run의 완료 상태를 구별하라.

## 구조화된 출력

아래 필드를 채운 연구 브리프를 반환하라. 실제 저장 도구가 없으면 응답 내 초안으로 표시하라.

| 필드 | 기록할 내용 |
|---|---|
| question | 검증할 질문 한 문장 |
| deliverable | 원하는 산출물과 형식 |
| scope | 대상·기간·변수·단위·제외 범위 |
| inputs | 출처·file ID·버전·접근 여부 |
| facts_and_assumptions | 확인한 사실과 진행 가정 |
| acceptance | 완료 검사와 수치 허용오차가 필요한 항목 |
| capabilities | 관측된 도구·부족한 기능·확인 시점 |
| unresolved | 진행을 막는 질문과 영향 |
| next_action | 가능한 첫 행동 또는 미지원 기능에 대한 제안 |
| scope_ids | 관측한 project/session/run ID 또는 null |

## 자체 예시와 인수 조건

사용자가 두 측정 CSV를 주며 “어느 조건이 더 좋은지 확인해 줘”라고 요청했다고 가정하라.
좋음의 의미·측정 단위·반복 측정 여부를 확인하고, 평균 비교와 인과 판단을 구별하라.
현재 도구로 가능한 기술통계부터 제안하되, 검정이나 일반 코드 실행을 이미 수행했다고 쓰지 마라.
브리프에 실제 파일 참조, 명시적 가정, 검사 가능한 완료 기준이 있으면 준비됐다고 판단하라.
자료를 읽지 못했거나 핵심 변수 정의가 없으면 그 항목을 미해결로 남겨라.
