# Local credentials and legacy Keychain import

Athena initializes its own credentials on startup. No Keychain access, environment variable or password is required for normal app startup, token refresh, or subsequent launch. On macOS the default store is `~/Library/Application Support/Athena/auth/credentials.v2.json`. On Windows it is `%USERPROFILE%\.athena\workspace\auth\credentials.v2.json`; Linux browser development also uses the workspace's `auth/` subdirectory. A separate workspace selected by the host uses its own `auth/` subdirectory on every platform. Model profile metadata and conversations retain their existing workspace locations.

## Security boundary

The file is **not encrypted**. It contains API keys and OAuth tokens. On macOS/Linux, Athena requires an owner-only directory (`0700`) and file (`0600`) and verifies ownership. On Windows, Node mode bits cannot represent this boundary: Athena checks the actual DACL and owner SID, allowing only the current user, SYSTEM and Administrators. Newly created private directories/files are secured before sensitive bytes are written; unsafe existing stores are rejected without automatically rewriting their permissions. Symbolic links and Windows reparse points are rejected. The permissions do not protect against code running as the same OS user, an administrator, or copies made by backups. Do not share this directory or include it in diagnostic archives. FileVault and BitLocker can protect locked disks; they do not protect an unlocked user session against programs running as that user.

Credential writes hold an OS-released lock across the complete read, update, and replace operation, including OAuth refresh. Athena writes a private temporary file, synchronizes it, and atomically replaces the old file. POSIX also synchronizes the parent directory; Node does not expose that directory operation on Windows, so this is not a claim of identical power-loss durability. It rejects damaged data or unsafe permissions rather than silently resetting the store. Provider or registration identities are used as keys; authentication values are not placed in the workspace event log or returned in provider lists. A restored credential can still expire or be revoked by its provider.

On Windows, the prepared `windows-private-storage.exe` performs each owner and DACL check through the system's managed access-control APIs. Every access still performs a fresh check; permission results are not cached. The helper accepts a fixed operation and a bounded path on standard input, without evaluating shell text. It is built from Athena-owned source and included with its configuration in the application. Missing or invalid helper files fail closed. This avoids starting a full PowerShell process for every credential read while retaining the existing file and permission validation.

## Import an older login

If Settings → Models offers **Approve import from Keychain**, selecting it lets the app request the existing Athena Keychain item. macOS may require your consent. Do not supply your Keychain password or a token to anyone outside the macOS approval screen. Athena never provisions or deletes a legacy item in this flow. It opens the encrypted `provider-secrets.v1` read-only; after a successful decode, it copies only entries missing from the new store and checks that they can be read back. Existing local logins take precedence. The old vault and its key are not deleted or changed.

You can skip the import and use Athena normally. If the matching key is unavailable, a provider must be reconnected through its supported sign-in method. Providers that require an API key need it entered once, directly in Athena Settings. A restored profile does not mean its provider is authenticated. Real Keychain approval is separate from automated tests, which use synthetic keys and isolated files.
